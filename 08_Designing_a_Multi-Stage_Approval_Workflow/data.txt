# Migration Guide: Moving from Billing API v1 to Billing API v2

## Overview
Billing API v2 introduces improved safety, clearer data models, and stronger guarantees around duplicate charge prevention. This guide walks you through the required changes when migrating from v1 to v2 and outlines best practices for a safe and reliable transition.

## Key Changes at a Glance
- All write operations to `/v2/charges` require an `Idempotency-Key` header.
- Legacy `/v1/charges` endpoints will be deprecated after the announced transition period.
- Invoice access is standardized through `/v2/invoices` endpoints.

## Required Client Updates
- Update request headers to include a unique `Idempotency-Key` for each charge creation.
- Replace the `currency` field with `currency_code` (ISO-4217 format).
- Update webhook handlers to listen for `invoice.paid.v2` events.

## Migration Steps
1. Update SDKs or client libraries to support required headers and schema changes.
2. Validate integrations in a non-production environment.
3. Gradually transition traffic to v2 endpoints.
4. Monitor error responses and retry behavior.
5. Complete migration before v1 endpoints are retired.

## Security and Compliance Notes
- Do not include customer PII, secrets, or tokens in logs or documentation.
- Avoid referencing internal system names or infrastructure details.
- Treat idempotency values as sensitive operational data.

## Known Limitations
- Invoice search currently returns a limited number of results.
- Risk evaluation data may not always be present during upstream disruptions.

## Summary
Billing API v2 provides safer charge handling and a more consistent interface. Following the steps above will help ensure a smooth migration with minimal disruption.
